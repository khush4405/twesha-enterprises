# Star Instruments Site — Architecture Blueprint & Rebuild Prompts

Reverse-engineered from the live site (star-instruments-ten.vercel.app). Colors are deliberately excluded from Part 2 — only layout, hierarchy, and component behavior are captured, so you can drop in your own palette using Part 3.

---

## PART 1 — How the site actually works (multi-level architecture)

### 1.1 Stack signals
Next.js (App Router — `/_next/image` optimized images, file-based dynamic routes), component-driven UI (Tailwind-style utility spacing is a safe bet), content is **data-driven** rather than hand-built per page — every category/subcategory page shares the exact same template, which only makes sense if one component renders from a nested JSON/config tree.

### 1.2 The real route structure
It looks like 4 "levels," but it's actually **2 templates**, one of them recursive:

```
/                                          → Home template (unique, marketing landing)
/about, /certificates, /videos,
/clients, /gallery, /contact               → Static content templates (unique per page)

/products                                  → Catalog INDEX template
/products/[...slugPath]                    → ONE recursive "Catalog Node" template, reused
                                              at any depth:
   /products/[category]
   /products/[category]/[subcategory]
   /products/[category]/[subcategory]/[sub-subcategory]  (if it existed)

   → When the matched node has CHILD categories:
        renders a "Categories" grid (one card per child)
   → When the matched node has LEAF products attached:
        renders a "Products" grid (one card per product)
   → Both sections can appear on the same page (confirmed: Flow Measurement
     shows sub-categories AND its own direct products together)
   → When the matched node IS a leaf product (no children):
        template switches to "Product Detail" mode — image, tabs, specs
```

This single-template-plus-data-tree approach is *why* the UI feels perfectly consistent no matter how deep you go — there's only one component making the decision, not five different developers building five different pages.

### 1.3 Underlying data model (inferred)
```ts
type CatalogNode = {
  slug: string
  name: string
  shortDescription?: string       // shown under H1 on category pages
  heroImage?: string
  children?: CatalogNode[]        // → renders "Categories" grid
  products?: ProductNode[]        // → renders "Products" grid
}

type ProductNode = {
  slug: string
  name: string
  cardBlurb: string               // 1-liner used on cards
  image: string
  description: string             // long-form, tab 1
  specifications: { label: string; value: string }[]  // tab 2
  documents?: { label: string; url: string }[]         // tab 4
}
```
Breadcrumbs are generated by walking the slug path against this tree — that's why every level's breadcrumb correctly chains `Products / Category / Subcategory / Product Name`.

### 1.4 Consistent UI system (what repeats on every page)
| Component | Behavior |
|---|---|
| **Sticky header** | Logo, Home/About links, "Products" (dropdown/mega-menu), Certificates/Videos/Clients/Contact, a filled "Request Quote" button pinned right |
| **Breadcrumb bar** | Appears on every non-home page; depth grows by one segment per level; last segment is plain text (not a link) |
| **Category card — compact variant** (Home only) | Image/icon, name, "N Types" count badge, 3 sample items + "+N more," single CTA link |
| **Category card — full variant** (`/products` index) | Same info but inline full comma-separated list instead of a badge + bullets, CTA reads "Explore Category" |
| **Product card** | Image, name, single-sentence blurb, whole card is a link |
| **Animated stat counters** | Homepage stats (Years/Installations/Factory Tested/Clients) render "0" first, then count up on scroll-into-view — a client-side counter component, not static text |
| **Tabbed product detail** | 4 tabs: Description / Key Specifications / Send Inquiry / Documentation, all on one page, no reload |
| **Conversion banner** | "Ready to Discuss Your Instrumentation Needs?" + Get a Quote / WhatsApp Us — **identical component reused on literally every page**, including deep product pages |
| **Footer** | 4 columns: brand blurb + cert badges, Get In Touch (phone/email/address), Quick Links, Our Products (mirrors top-level categories) + bottom copyright bar |
| **Logo marquee** | Client logos on Home scroll infinitely (list is duplicated in the DOM to loop seamlessly) |

### 1.5 Why it feels "consistent"
Three mechanisms, not luck:
1. **One data tree** drives every catalog page (Section 1.3) — content changes, template doesn't.
2. **One conversion banner + footer** are composed into every template regardless of level.
3. **Card components are shared** — the same `ProductCard`/`CategoryCard` is reused across Home, `/products`, and every nested category page, just fed different data.

## PART 2 — Prompt to clone the *architecture only* (no brand colors)

Copy this into Claude Code / Cursor / v0 / Bolt / Lovable. It deliberately uses a neutral grayscale placeholder theme so nothing here locks you into Star Instruments' colors.

```
Build a multi-level B2B product catalog website using Next.js (App Router) +
TypeScript + Tailwind CSS. Do NOT invent a brand color palette — use only
neutral placeholder tokens for now (see the theme block below). I will
restyle colors in a separate pass, so keep every color reference tied to a
CSS variable / Tailwind theme token, never a hardcoded hex value in a
component.

PLACEHOLDER THEME (put these in globals.css as CSS variables and mirror them
in tailwind.config.ts under theme.extend.colors — do not use raw hexes
anywhere else):
  --color-primary: #4b5563       (slate gray — stand-in for brand primary)
  --color-primary-dark: #374151
  --color-accent: #6b7280        (stand-in for brand accent)
  --color-surface: #ffffff
  --color-surface-muted: #f3f4f6
  --color-border: #e5e7eb
  --color-text: #111827
  --color-text-muted: #6b7280
  --color-text-inverse: #ffffff

DATA MODEL
Create a typed content tree (a TS/JSON config, not hardcoded JSX) shaped like:
  CatalogNode { slug, name, shortDescription?, heroImage?, children?: CatalogNode[], products?: ProductNode[] }
  ProductNode { slug, name, cardBlurb, image, description, specifications: {label, value}[], documents?: {label, url}[] }
Seed it with 5-7 top-level categories, 2-4 subcategories under at least one
category, and 3-6 leaf products under a few nodes — mix nodes that have BOTH
child categories and direct products, and nodes that only have direct
products (no subcategories), so the template handles both cases.

ROUTES
  /                                    Home
  /products                           Catalog index — full-variant cards for
                                       every top-level category
  /products/[...slug]                 ONE recursive catalog template:
                                         - resolve the slug path against the
                                           data tree
                                         - if node.children exists → render a
                                           "Categories" grid section
                                         - if node.products exists → render a
                                           "Products" grid section (both
                                           sections can appear together)
                                         - if the resolved node is itself a
                                           leaf product → render the Product
                                           Detail layout instead (image, tabs)
                                       Breadcrumb must reflect actual depth by
                                       walking the resolved path, each
                                       segment except the last is a link.

COMPONENTS TO BUILD (shared/reused, not duplicated per page)
  - Header: sticky, logo, nav links, a "Products" dropdown, a filled CTA
    button on the right, mobile hamburger menu
  - Breadcrumb: takes an array of {label, href?} and renders "/"-separated,
    last item unlinked
  - CategoryCardCompact: image, name, count badge ("N Types"), 3 sample
    child/product names + "+N more", one CTA link — used on Home only
  - CategoryCardFull: image, name, full inline list of children, "Explore
    Category" CTA — used on /products index and inside catalog pages
  - ProductCard: image, name, one-line blurb, whole card clickable
  - StatCounter: animates from 0 to a target number when scrolled into view
    (use IntersectionObserver + requestAnimationFrame or a small counting
    hook — no external libs required)
  - ProductTabs: client component, 4 tabs (Description / Key Specifications /
    Send Inquiry / Documentation), no page reload, keyboard-accessible
    (role="tablist"/"tab"/"tabpanel")
  - ConversionBanner: heading + subtext + two buttons (primary "Get a Quote"
    → contact route, secondary "WhatsApp Us" → wa.me link) — compose this
    into EVERY page template, including the deepest product page
  - Footer: 4-column layout — brand blurb + certification badges, contact
    details, quick links, top-level category links — plus a bottom bar

HOME PAGE SECTIONS (in order)
  1. Hero: eyebrow badge, two-line H1, subtext, two CTA buttons
  2. Stats bar using StatCounter (4 stats + one static badge)
  3. "Portfolio" section: CategoryCardCompact grid, one card per top-level
     category
  4. "Why choose us" feature grid (6 short value-prop cards, icon + 1-2
     lines each)
  5. "Industries served" — small icon/label chips, no long copy
  6. Logo marquee — infinite horizontal scroll of client/partner logos
     (duplicate the list in the DOM for a seamless loop)
  7. ConversionBanner
  8. Footer

RESPONSIVE RULES
  - Grids collapse from 3-4 columns → 2 → 1 as viewport narrows
  - Header collapses to a hamburger drawer below md breakpoint
  - Tabs on product detail become a vertical accordion on small screens
    (or keep as scrollable tabs — your call, just keep them usable)

ACCEPTANCE CRITERIA
  - Every catalog-level page (any depth) is served by the SAME route
    component, not one file per level
  - No hardcoded color hex values inside component files — only the
    CSS-variable-backed Tailwind tokens above
  - ConversionBanner and Footer appear on every route with zero duplicated
    markup (import the shared component, don't copy-paste it)
  - Adding a new category or a new nested subcategory to the data file
    requires editing ONLY the data file — zero new route files, zero new
    components
```

## PART 3 — Prompt to apply *your own* color palette (Phase 2)

Run this **after** Prompt A has produced a working neutral build. It touches only color tokens — no structure, spacing, or component changes.

```
Do not change any component structure, layout, spacing, copy, or markup.
Only update the color tokens defined in globals.css (:root CSS variables)
and the matching entries in tailwind.config.ts theme.extend.colors.

Replace the placeholder palette with this one:
  --color-primary:        [YOUR BRAND PRIMARY, e.g. #0F4C81]
  --color-primary-dark:   [a ~15% darker shade of primary, for hover/active]
  --color-accent:         [YOUR SECONDARY/ACCENT COLOR]
  --color-surface:        [main background, usually white or near-white]
  --color-surface-muted:  [light tinted background for alternating sections]
  --color-border:         [subtle border/divider color]
  --color-text:           [primary body text color, near-black]
  --color-text-muted:     [secondary/caption text color]
  --color-text-inverse:   [text color used on top of --color-primary]
  --color-success:        [keep or restyle — used sparingly, e.g. "in stock"]
  --color-focus-ring:     [visible focus outline color for accessibility]

Apply the new tokens EVERYWHERE color currently appears, including (do not
skip any of these — this is the full list of places color shows up):
  - Header active nav-link state and the "Request Quote" button
  - Hero CTA buttons (primary filled + secondary outline/ghost)
  - StatCounter numbers and icon accents
  - "N Types" count badge background/text on category cards
  - Card hover state (border or shadow tint)
  - ProductTabs active tab underline/indicator
  - ConversionBanner background and its two buttons
  - Breadcrumb current-segment text color (if distinguished from links)
  - Link hover/underline color throughout body copy
  - Form/input focus rings on the contact and inquiry forms
  - Footer background (if it's a distinct tint, not plain white/black)
  - WhatsApp button — keep it recognizable (WhatsApp green is fine to leave
    as-is for user trust, unless you want full brand consistency instead)

If I haven't given you a full palette above, propose one based on [describe
your industry/brand vibe here, e.g. "a renewable-energy startup — modern,
trustworthy, slightly more vivid than corporate navy"] and list the hex
values you chose before applying them.

After applying, do a contrast pass: body text on its background must meet
WCAG AA (4.5:1), large text/icons must meet 3:1. Flag anything that fails
instead of silently leaving it.
```

## How to use these two prompts together
1. Run **Part 2** first in your tool of choice — you get the full working, click-through site (home → catalog → subcategory → product tabs) in a neutral gray theme.
2. Fill in your actual hex codes in **Part 3** (or describe your brand vibe and let the model propose a palette) and run it as a second pass on the same codebase.
3. Because Part 2 forces every color through CSS variables, Part 3 never has to touch component code — it's a find-and-replace at the token layer, so you can re-theme again later in seconds if you ever rebrand.
